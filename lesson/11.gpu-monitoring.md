## GPU 모니터링: DCGM Exporter + Prometheus + Grafana ##

kubelet과 node-exporter는 GPU 지표를 주지 않는다. 그래서 GPU 노드마다 NVIDIA DCGM Exporter를 DaemonSet으로 띄우고, 이미 설치한 Prometheus가 GPU 지표를 수집하게 한다. 이 장에서는 다음을 차례로 만든다.

- 수집할 지표와 각 지표를 보는 이유
- GPU 장애를 판단하는 기준
- 상황별 PromQL
- 알림 규칙
- Grafana 대시보드

### 지표 계층 ###

GPU 장애와 성능 문제는 한 지표에만 나타나지 않는다. 아래 네 계층을 함께 본다.

| 계층 | 수집 도구 | 대표 지표 | 보는 이유 |
|---|---|---|---|
| GPU 하드웨어 | DCGM Exporter (이 장에서 설치) | 사용률, 메모리, 온도, 전력, 클럭, XID, ECC | GPU 자체의 상태와 하드웨어 장애 |
| 쿠버네티스 | kube-state-metrics (설치됨) | GPU 용량·할당 가능 수·요청 수, 노드 상태 | 스케줄러가 보는 GPU 상태 |
| 노드 | node-exporter (설치됨) | CPU, 메모리, 디스크, 네트워크 | GPU 밖의 병목(디스크 가득 참, CPU 포화) |
| 추론 서비스 | vLLM `/metrics` (KEDA 장에서 수집) | 동시 요청, KV 캐시, 토큰 처리량, TTFT | 실제 부하와 사용자가 느끼는 품질 |

### DCGM Exporter 4.9.0의 지표 이름 ###

DCGM Exporter 4.9.0(2026-11-06)부터 기본 지표의 이름과 단위가 바뀌었다. 인터넷의 예전 자료와 대시보드는 옛 이름을 쓰므로 그대로 쓰면 데이터가 나오지 않는다.

| 예전 이름 (4.8.x 이하) | 4.9.0 이름 | 단위 변화 |
|---|---|---|
| `DCGM_FI_DEV_GPU_UTIL` | `DCGM_FI_DEV_GPU_UTIL_RATIO` | % → 0~1 비율 |
| `DCGM_FI_DEV_FB_USED` | `DCGM_FI_DEV_FB_USED_BYTES` | MiB → bytes |
| `DCGM_FI_DEV_GPU_TEMP` | `DCGM_FI_DEV_GPU_TEMP_CELSIUS` | 같음 (°C) |
| `DCGM_FI_DEV_POWER_USAGE` | `DCGM_FI_DEV_BOARD_POWER_WATTS` | 같음 (W) |
| `DCGM_FI_DEV_SM_CLOCK` | `DCGM_FI_DEV_SM_CLOCK_HERTZ` | MHz → Hz |
| `DCGM_FI_DEV_TOTAL_ENERGY_CONSUMPTION` | `DCGM_FI_DEV_GPU_ENERGY_JOULES_TOTAL` | mJ → J |
| `DCGM_FI_DEV_XID_ERRORS` | `DCGM_FI_DEV_XID_ERROR` | 같음 (마지막 XID 코드) |
| `DCGM_FI_PROF_DRAM_ACTIVE` | `DCGM_FI_PROF_DRAM_UTIL_RATIO` | 같음 (0~1) |

### 1. 수집할 GPU 지표 ###

| 분류 | 지표 | 뜻 | 볼 때 주의할 점 |
|---|---|---|---|
| 사용률 | `DCGM_FI_DEV_GPU_UTIL_RATIO` | 커널이 하나라도 돌던 시간의 비율 | vLLM은 요청이 조금만 있어도 1에 가깝게 나온다. 부하 지표로 쓰지 않는다. |
| 사용률 | `DCGM_FI_PROF_SM_UTIL_RATIO` | SM에 워프가 하나 이상 있던 사이클 비율 | GPU_UTIL보다 실제 연산량에 가깝다. |
| 사용률 | `DCGM_FI_PROF_TENSOR_UTIL_RATIO` | 텐서 코어 파이프가 활성인 사이클 비율 | 행렬곱이 많은 prefill 구간에 오른다. |
| 사용률 | `DCGM_FI_PROF_DRAM_UTIL_RATIO` | GPU 메모리 인터페이스가 데이터를 주고받은 사이클 비율 | decode는 메모리 대역폭에 묶이므로 동시 요청이 늘면 함께 오른다. 포화를 판단할 때 가장 쓸모 있다. |
| 메모리 | `DCGM_FI_DEV_FB_USED_BYTES`, `_FB_CAPACITY_BYTES` | GPU 메모리 사용량과 전체 용량 | vLLM은 기동할 때 메모리의 90%(`--gpu-memory-utilization` 기본 0.9)를 KV 캐시용으로 미리 잡는다. 그래서 사용량이 거의 일정하고, 실제 부하는 `vllm:kv_cache_usage_perc`로 본다. |
| 온도 | `DCGM_FI_DEV_GPU_TEMP_CELSIUS`, `_MEMORY_TEMP_CELSIUS` | GPU 코어·메모리 온도 | 85°C를 넘는 상태가 이어지면 스로틀링이 시작된다. |
| 전력 | `DCGM_FI_DEV_BOARD_POWER_WATTS`, `_BOARD_POWER_LIMIT_ENFORCED_WATTS` | 소비 전력과 적용 중인 전력 한도 | L40S의 최대 전력은 350W다. 한도에 붙어 있으면 전력 제한으로 클럭이 낮아진다. |
| 클럭 | `DCGM_FI_DEV_SM_CLOCK_HERTZ` | SM 클럭 | 부하 중에 클럭이 떨어지면 스로틀링이다. |
| 스로틀링 | `DCGM_FI_DEV_GPU_THERMAL_THROTTLE_SECONDS_TOTAL`, `_POWER_THROTTLE_SECONDS_TOTAL` | 온도·전력 정책으로 클럭이 낮아진 누적 시간 | `rate()`를 취하면 스로틀링된 시간 비율이 된다. |
| 에너지 | `DCGM_FI_DEV_GPU_ENERGY_JOULES_TOTAL` | 드라이버가 로드된 뒤 쓴 에너지 | 토큰당 에너지, kWh 계산에 쓴다. |
| PCIe | `DCGM_FI_PROF_PCIE_RX_BYTES`, `_TX_BYTES` | PCIe 수신·송신 속도(bytes/s) | 기동 때 S3에서 가중치를 GPU로 올리면 RX가 크게 오른다. |
| PCIe | `DCGM_FI_DEV_PCIE_REPLAY_TOTAL` | PCIe 재전송 누적 횟수 | 계속 늘면 PCIe 링크 문제다. |
| 오류 | `DCGM_FI_DEV_XID_ERROR` | 마지막으로 발생한 XID 코드 | 0이면 없음. 코드별 의미는 6절에 있다. |
| 오류 | `DCGM_FI_DEV_ECC_DBE_VOL_TOTAL`, `_ECC_SBE_VOL_TOTAL` | 정정 불가(DBE)·정정된(SBE) 메모리 오류 수 | 기본 목록에는 없어서 2절에서 추가한다. ECC가 꺼진 GPU에서는 나오지 않는다. |
| 오류 | `DCGM_FI_DEV_ROW_REMAP_UNCORRECTABLE_TOTAL`, `_ROW_REMAP_FAILED` | 메모리 행 리매핑 횟수와 실패 여부 | 행 리매핑을 지원하는 GPU에서만 나온다. |

DCGM 지표에는 아래 레이블이 붙는다. 실제 레이블은 3절의 조회 결과에서 확인한다.

| 레이블 | 값 |
|---|---|
| `gpu` | 노드 안의 GPU 번호. g6e.4xlarge는 `0` 하나 |
| `hostname` | DCGM Exporter가 붙이는 노드 이름 |
| `node` | 2절의 ServiceMonitor 설정으로 붙이는 노드 이름. kube-state-metrics 지표와 같은 레이블이라 조인할 때 쓴다. |
| `exported_namespace`, `exported_pod`, `exported_container` | 그 GPU를 쓰는 파드. Prometheus가 수집 대상(DCGM Exporter 파드)의 `namespace`, `pod` 레이블을 먼저 붙이므로 `exported_` 접두사가 붙는다. GPU를 쓰는 파드가 없으면 비어 있다. |

### 2. DCGM Exporter 설치 ###

#### 2.1 환경 설정 ####

```
export DCGM_EXPORTER_VERSION="4.9.0"

# GPU 노드 확인 (vLLM 파드가 떠 있으면 하나 이상 나온다)
kubectl get nodes -l karpenter.sh/nodepool=gpu
```

#### 2.2 설정 파일 ####

차트의 기본 지표 목록에는 ECC 오류와 스로틀링 시간이 빠져 있다. 1절의 지표를 모두 받도록 지표 목록을 직접 적는다. `config.metrics`는 목록이라 Helm이 통째로 바꾸므로, 수집할 지표를 빠짐없이 적는다.

```
cat > dcgm-exporter-values.yaml <<'EOF'
# GPU 노드에만 띄운다 (vLLM과 같은 Karpenter 노드풀)
nodeSelector:
  karpenter.sh/nodepool: gpu
tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule

serviceMonitor:
  enabled: true
  interval: 30s
  relabelings:
    # 파드가 떠 있는 노드 이름을 node 레이블로 붙인다 (kube-state-metrics와 조인할 때 쓴다)
    - sourceLabels: [__meta_kubernetes_pod_node_name]
      targetLabel: node
      action: replace

config:
  metrics:
    - name: default
      every: 30s
      enrichment:
        kubernetes: auto        # GPU를 쓰는 파드의 pod, namespace, container 레이블
        container: false
        dra: false
        hpc_jobs: false
      fields:
        # 사용률
        - {name: DCGM_FI_DEV_GPU_UTIL_RATIO, prometheus_type: gauge, help: GPU utilization ratio.}
        - {name: DCGM_FI_DEV_MEMORY_UTIL_RATIO, prometheus_type: gauge, help: Memory utilization ratio.}
        - {name: DCGM_FI_PROF_GR_ENGINE_UTIL_RATIO, prometheus_type: gauge, help: Graphics engine active ratio.}
        - {name: DCGM_FI_PROF_SM_UTIL_RATIO, prometheus_type: gauge, help: SM active ratio.}
        - {name: DCGM_FI_PROF_TENSOR_UTIL_RATIO, prometheus_type: gauge, help: Tensor pipe active ratio.}
        - {name: DCGM_FI_PROF_DRAM_UTIL_RATIO, prometheus_type: gauge, help: Device memory interface active ratio.}
        # 메모리
        - {name: DCGM_FI_DEV_FB_CAPACITY_BYTES, prometheus_type: gauge, help: Total framebuffer capacity in bytes.}
        - {name: DCGM_FI_DEV_FB_USED_BYTES, prometheus_type: gauge, help: Used framebuffer memory in bytes.}
        - {name: DCGM_FI_DEV_FB_FREE_BYTES, prometheus_type: gauge, help: Free framebuffer memory in bytes.}
        # 온도, 전력, 클럭, 스로틀링
        - {name: DCGM_FI_DEV_GPU_TEMP_CELSIUS, prometheus_type: gauge, help: GPU temperature in C.}
        - {name: DCGM_FI_DEV_MEMORY_TEMP_CELSIUS, prometheus_type: gauge, help: Memory temperature in C.}
        - {name: DCGM_FI_DEV_BOARD_POWER_WATTS, prometheus_type: gauge, help: Power draw in W.}
        - {name: DCGM_FI_DEV_BOARD_POWER_LIMIT_ENFORCED_WATTS, prometheus_type: gauge, help: Enforced power limit in W.}
        - {name: DCGM_FI_DEV_GPU_ENERGY_JOULES_TOTAL, prometheus_type: counter, help: Energy consumed in joules.}
        - {name: DCGM_FI_DEV_SM_CLOCK_HERTZ, prometheus_type: gauge, help: SM clock in hertz.}
        - {name: DCGM_FI_DEV_MEMORY_CLOCK_HERTZ, prometheus_type: gauge, help: Memory clock in hertz.}
        - {name: DCGM_FI_DEV_GPU_THERMAL_THROTTLE_SECONDS_TOTAL, prometheus_type: counter, help: Time throttled by thermal policy in seconds.}
        - {name: DCGM_FI_DEV_GPU_POWER_THROTTLE_SECONDS_TOTAL, prometheus_type: counter, help: Time throttled by power policy in seconds.}
        # PCIe
        - {name: DCGM_FI_PROF_PCIE_TX_BYTES, prometheus_type: gauge, help: PCIe transmit rate in bytes per second.}
        - {name: DCGM_FI_PROF_PCIE_RX_BYTES, prometheus_type: gauge, help: PCIe receive rate in bytes per second.}
        - {name: DCGM_FI_DEV_PCIE_REPLAY_TOTAL, prometheus_type: counter, help: Total number of PCIe retries.}
        # 오류
        - {name: DCGM_FI_DEV_XID_ERROR, prometheus_type: gauge, help: Value of the last XID error.}
        - {name: DCGM_FI_DEV_ECC_SBE_VOL_TOTAL, prometheus_type: counter, help: Single-bit volatile ECC errors.}
        - {name: DCGM_FI_DEV_ECC_DBE_VOL_TOTAL, prometheus_type: counter, help: Double-bit volatile ECC errors.}
        - {name: DCGM_FI_DEV_ROW_REMAP_UNCORRECTABLE_TOTAL, prometheus_type: counter, help: Rows remapped for uncorrectable errors.}
        - {name: DCGM_FI_DEV_ROW_REMAP_CORRECTABLE_TOTAL, prometheus_type: counter, help: Rows remapped for correctable errors.}
        - {name: DCGM_FI_DEV_ROW_REMAP_FAILED, prometheus_type: gauge, help: Whether row remapping has failed.}
EOF
```

| 설정 | 설명 |
|---|---|
| `nodeSelector`, `tolerations` | GPU 노드에는 `nvidia.com/gpu` 테인트가 있어서 이를 허용해야 뜬다. CPU 노드에는 띄우지 않는다. |
| `serviceMonitor` | kube-prometheus-stack이 레이블과 상관없이 모든 ServiceMonitor를 수집하도록 설정했으므로(KEDA 장 2절) 추가 레이블은 필요 없다. |
| `every: 30s` | DCGM이 GPU에서 값을 읽는 주기. Prometheus 수집 주기(30s)와 맞춘다. |
| `enrichment.kubernetes: auto` | kubelet의 pod-resources API로 GPU를 쓰는 파드를 찾아 레이블로 붙인다. |
| `DCGM_FI_PROF_*` | 프로파일링(DCP) 지표다. 차트 기본 설정이 컨테이너에 `SYS_ADMIN` 권한을 주는 이유다. |

#### 2.3 설치 ####

```
helm repo add gpu-helm-charts https://nvidia.github.io/dcgm-exporter/helm-charts
helm repo update

helm install dcgm-exporter gpu-helm-charts/dcgm-exporter \
  -n monitoring \
  --version ${DCGM_EXPORTER_VERSION} \
  -f dcgm-exporter-values.yaml

kubectl rollout status daemonset/dcgm-exporter -n monitoring
kubectl get pods -n monitoring -l app.kubernetes.io/name=dcgm-exporter -o wide
```

[예상 결과]
```
NAME                  READY   STATUS    RESTARTS   AGE   IP          NODE
dcgm-exporter-<해시>   1/1     Running   0          1m    <파드 IP>   <GPU 노드 이름>
```

- **파드 수:** GPU 노드마다 파드가 하나씩 뜬다. Karpenter가 GPU 노드를 늘리면 DaemonSet 파드도 따라 늘어난다.
- **GPU 할당:** DCGM Exporter는 `nvidia.com/gpu`를 요청하지 않는다. 그래서 vLLM이 쓸 GPU를 빼앗지 않는다.

### 3. 수집 확인 ###

먼저 DCGM Exporter가 내보내는 값을 직접 본다.

```
kubectl -n monitoring port-forward daemonset/dcgm-exporter 9400:9400 >/dev/null 2>&1 &
PF_PID=$!; sleep 3

curl -s localhost:9400/metrics \
  | grep -E '^DCGM_FI_DEV_(GPU_TEMP_CELSIUS|BOARD_POWER_WATTS|GPU_UTIL_RATIO|XID_ERROR|ECC_DBE_VOL_TOTAL)'

kill ${PF_PID}
```

[예상 결과] (레이블과 값은 환경마다 다르다)
```
DCGM_FI_DEV_GPU_TEMP_CELSIUS{gpu="0",hostname="<GPU 노드 이름>",...,namespace="llm-serving",pod="gemma4-12b-vllm-<해시>",...} 34
DCGM_FI_DEV_BOARD_POWER_WATTS{gpu="0",...} 78.5
DCGM_FI_DEV_GPU_UTIL_RATIO{gpu="0",...} 0
DCGM_FI_DEV_XID_ERROR{gpu="0",...} 0
```

- **파드 레이블:** vLLM 파드가 이 GPU를 쓰고 있으면 `namespace="llm-serving"`, `pod="gemma4-12b-vllm-..."` 레이블이 보인다. Prometheus에 저장될 때는 `exported_namespace`, `exported_pod`가 된다.
- **ECC 지표가 없을 때:** 그 GPU의 ECC가 꺼져 있거나 필드를 지원하지 않는 것이다. 다른 지표는 그대로 나온다.

다음으로 Prometheus가 수집하는지 본다.

```
kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090:9090 >/dev/null 2>&1 &
PROM_PID=$!; sleep 3

# 수집 대상 상태 (health가 up이어야 한다)
curl -s 'http://localhost:9090/api/v1/targets?state=active' | jq -r '
  .data.activeTargets[] | select(.labels.job == "dcgm-exporter")
  | "\(.labels.node)  \(.health)  \(.lastError)"'

# 노드별 GPU 수 (g6e.4xlarge는 1)
curl -s http://localhost:9090/api/v1/query \
  --data-urlencode 'query=count by (node) (DCGM_FI_DEV_GPU_TEMP_CELSIUS)' \
  | jq -r '.data.result[] | "\(.metric.node)  \(.value[1])"'
```

이 port-forward(`PROM_PID`)는 4절과 7절에서도 쓰므로 열어 둔다.

### 4. PromQL: 무엇을 뽑아 보나 ###

질문별로 정리했다. Prometheus UI의 Graph 탭이나 Grafana Explore에 그대로 넣으면 된다.

#### 4.1 GPU가 얼마나 바쁜가 ####

```
# GPU 사용률 (0~1). vLLM은 요청이 조금만 있어도 1에 가깝다
avg by (node, gpu) (DCGM_FI_DEV_GPU_UTIL_RATIO)

# 실제 연산과 메모리 대역폭 사용 비율 (DCP 지표)
avg by (node, gpu) (DCGM_FI_PROF_SM_UTIL_RATIO)
avg by (node, gpu) (DCGM_FI_PROF_TENSOR_UTIL_RATIO)
avg by (node, gpu) (DCGM_FI_PROF_DRAM_UTIL_RATIO)
```

decode 단계는 토큰마다 가중치 전체를 GPU 메모리에서 읽는다. 그래서 동시 요청이 늘수록 `DRAM_UTIL_RATIO`가 올라가고, 1에 가까워지면 그 GPU의 대역폭이 포화된 것이다.

#### 4.2 GPU 메모리와 KV 캐시 ####

```
# GPU 메모리 사용 비율. vLLM은 기동 직후 약 0.9로 고정된다
sum by (node, gpu) (DCGM_FI_DEV_FB_USED_BYTES) / sum by (node, gpu) (DCGM_FI_DEV_FB_CAPACITY_BYTES)

# 실제 부하는 vLLM KV 캐시 사용률로 본다 (0~1)
max by (pod) (vllm:kv_cache_usage_perc{namespace="llm-serving"})
```

#### 4.3 온도, 전력, 클럭, 스로틀링 ####

```
max by (node, gpu) (DCGM_FI_DEV_GPU_TEMP_CELSIUS)
max by (node, gpu) (DCGM_FI_DEV_MEMORY_TEMP_CELSIUS)

# 소비 전력과 전력 한도 대비 비율
avg by (node, gpu) (DCGM_FI_DEV_BOARD_POWER_WATTS)
avg by (node, gpu) (DCGM_FI_DEV_BOARD_POWER_WATTS) / avg by (node, gpu) (DCGM_FI_DEV_BOARD_POWER_LIMIT_ENFORCED_WATTS)

# SM 클럭 (Hz). 부하 중에 떨어지면 스로틀링
avg by (node, gpu) (DCGM_FI_DEV_SM_CLOCK_HERTZ)

# 최근 5분 중 온도·전력 때문에 클럭이 낮아진 시간 비율 (0~1)
rate(DCGM_FI_DEV_GPU_THERMAL_THROTTLE_SECONDS_TOTAL[5m])
rate(DCGM_FI_DEV_GPU_POWER_THROTTLE_SECONDS_TOTAL[5m])
```

#### 4.4 PCIe ####

```
# 호스트 → GPU 전송 속도 (bytes/s). 모델 가중치를 올릴 때 크게 오른다
sum by (node) (DCGM_FI_PROF_PCIE_RX_BYTES)

# 최근 1시간의 PCIe 재전송 횟수. 계속 늘면 링크 문제
increase(DCGM_FI_DEV_PCIE_REPLAY_TOTAL[1h])
```

#### 4.5 어느 파드가 어느 GPU를 쓰나 ####

```
max by (node, gpu, exported_namespace, exported_pod) (DCGM_FI_DEV_GPU_UTIL_RATIO{exported_pod!=""})
```

#### 4.6 쿠버네티스가 보는 GPU ####

```
# 노드별 GPU 용량과 할당 가능 수. 디바이스 플러그인이 고장 난 GPU를 빼면 할당 가능 수가 줄어든다
kube_node_status_capacity{resource="nvidia_com_gpu"}
kube_node_status_allocatable{resource="nvidia_com_gpu"}

# 클러스터 GPU 할당률 (요청한 GPU / 할당 가능한 GPU)
sum(kube_pod_container_resource_requests{resource="nvidia_com_gpu"})
  / sum(kube_node_status_allocatable{resource="nvidia_com_gpu"})
```

#### 4.7 추론 서비스와 함께 보기 ####

```
# 파드별 생성 토큰 처리량 (tokens/s)
sum by (pod) (rate(vllm:generation_tokens_total{namespace="llm-serving"}[1m]))

# 토큰 하나를 만드는 데 쓴 GPU 에너지 (J/token). 낮을수록 효율적이다
sum(rate(DCGM_FI_DEV_GPU_ENERGY_JOULES_TOTAL[5m]))
  / sum(rate(vllm:generation_tokens_total{namespace="llm-serving"}[5m]))

# 최근 1시간 동안 GPU가 쓴 에너지 (kWh)
sum by (node) (increase(DCGM_FI_DEV_GPU_ENERGY_JOULES_TOTAL[1h])) / 3.6e6
```

### 5. 날마다 볼 지표 ###

지표가 많아서 처음에는 아래 순서로 본다.

| 순서 | 지표 | 정상 | 의심할 상황 |
|---|---|---|---|
| 1 | 발생 중인 GPU 알림 수 (7절) | 0 | 1 이상이면 6절 절차로 대응 |
| 2 | `kube_node_status_allocatable{resource="nvidia_com_gpu"}` | 용량과 같음 | 용량보다 작으면 GPU가 고장으로 빠진 것 |
| 3 | `DCGM_FI_DEV_XID_ERROR` | 0 | 0이 아니면 6.1절의 코드표로 판단 |
| 4 | `vllm:kv_cache_usage_perc`, `vllm:num_requests_waiting` | 대기 0 근처 | 대기가 쌓이면 용량 부족 (KEDA 동작 확인) |
| 5 | `DCGM_FI_PROF_DRAM_UTIL_RATIO` | 부하에 비례 | 1 근처에 붙어 있으면 대역폭 포화 |
| 6 | `DCGM_FI_DEV_GPU_TEMP_CELSIUS` | 85°C 미만 | 85°C 이상이 이어지면 냉각 문제 |
| 7 | 스로틀링 시간 비율 | 0 | 0.1 이상이면 성능이 깎이는 중 |
| 8 | 토큰당 에너지 (J/token) | 평소 값과 비슷 | 평소보다 크게 오르면 스로틀링이나 비효율적인 배치 |

### 6. GPU 장애 판단 ###

GPU 장애는 다음 순서로 드러나는 경우가 많다.

1. 드라이버가 XID를 남긴다.
2. 디바이스 플러그인이 그 GPU를 unhealthy로 바꿔 할당 가능 수에서 뺀다.
3. vLLM이 멈추거나 재시작한다.

그래서 한 신호만 보지 말고 아래 신호를 함께 본다.

| 신호 | 판단 기준 (PromQL) | 뜻 |
|---|---|---|
| 하드웨어 XID | `DCGM_FI_DEV_XID_ERROR`가 6.1절의 하드웨어 코드 | GPU나 PCIe, 펌웨어 문제. 노드를 교체한다. |
| 애플리케이션 XID | `DCGM_FI_DEV_XID_ERROR`가 13, 31, 43, 45로 새로 바뀜 | 대부분 프로그램 쪽 오류. 같은 노드에서 반복되면 하드웨어를 의심한다. |
| 정정 불가 ECC | `increase(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL[10m]) > 0` | 메모리 데이터가 손상됐다. 노드를 교체한다. |
| 행 리매핑 실패 | `DCGM_FI_DEV_ROW_REMAP_FAILED == 1` | 더는 고장 난 메모리 행을 대체할 수 없다. 노드를 교체한다. |
| GPU 지표 사라짐 | GPU 용량이 있는 노드에 DCGM 지표가 없음 | GPU가 버스에서 떨어졌거나(XID 79) DCGM Exporter가 죽었다. |
| 할당 가능 GPU 감소 | `allocatable < capacity` | 디바이스 플러그인이 GPU를 unhealthy로 판단했다. 앱 오류 XID(13, 31, 43, 45 등)는 이 판단에서 빠진다. |
| 과열 | GPU 온도 85°C 초과가 5분 이상 | 냉각 문제. 스로틀링이 따라온다. |
| 스로틀링 | 온도 스로틀링 시간 비율 0.1 초과가 10분 이상 | 성능 저하. 온도와 전력을 함께 본다. |
| PCIe 재전송 지속 | 재전송이 30분 이상 계속 늘어남 | PCIe 링크 품질 문제 |
| vLLM 멈춤 | 처리 중인 요청이 있는데 생성 토큰이 5분 동안 0 | 엔진이나 GPU가 멈췄다. |
| 노드 NotReady | GPU 노드의 Ready 조건이 false | 노드 전체 장애 |

#### 6.1 대표 XID 코드 ####

| XID | 뜻 | 분류 |
|---|---|---|
| 13 | Graphics Engine Exception | 애플리케이션 (잘못된 명령, 메모리 접근 등) |
| 31 | GPU memory page fault | 애플리케이션 (잘못된 주소 접근) |
| 43 | GPU stopped processing | 애플리케이션 (프로세스 비정상 종료 등) |
| 45 | Preemptive cleanup | 앞선 오류 뒤의 정리 작업. 함께 나온 다른 XID를 본다. |
| 48 | Double Bit ECC Error | 하드웨어 (GPU 메모리) |
| 63 | ECC page retirement / row remapping 기록 | 메모리 오류를 대체 기록함. GPU 리셋 뒤 반영된다. |
| 64 | ECC page retirement / row remapping 실패 | 하드웨어 (GPU 메모리) |
| 79 | GPU has fallen off the bus | 하드웨어 또는 PCIe. 노드 재시작이나 교체가 필요하다. |
| 92 | High single-bit ECC error rate | 메모리 열화 징후 |
| 94 | Contained ECC error | 메모리 오류, 해당 프로세스만 영향 |
| 95 | Uncontained ECC error | 메모리 오류, GPU 전체 영향 |
| 119, 120 | GSP RPC timeout / GSP error | GPU 펌웨어(GSP) 오류 |
| 154 | GPU recovery action changed | 드라이버가 필요한 복구 조치(GPU 리셋, 노드 재부팅 등)를 알린다. |

같은 코드라도 드라이버 버전과 함께 나온 다른 XID에 따라 조치가 다를 수 있다. 정확한 조치는 NVIDIA XID 카탈로그를 따른다.

#### 6.2 장애가 났을 때 ####

1. 알림이나 대시보드에서 노드와 GPU를 확인한다. 알림 레이블의 `node`, `gpu`를 본다.

2. 노드를 지우기 전에 증거를 남긴다. 디버그 파드로 노드에 들어가 커널 로그의 XID와 GPU 상태를 저장한다.

   ```
   NODE=<노드 이름>

   kubectl debug node/${NODE} -it --profile=sysadmin \
     --image=public.ecr.aws/amazonlinux/amazonlinux:2023 -- \
     chroot /host sh -c 'dmesg -T | grep -i xid | tail -20; nvidia-smi -q -d ECC,TEMPERATURE,PERFORMANCE'
   ```

3. 새 스케줄을 막는다.

   ```
   kubectl cordon ${NODE}
   ```

4. vLLM 레플리카가 하나뿐이면 다른 노드에 파드를 먼저 띄운다. 새 GPU 노드와 파드가 준비되기까지 약 7분이 걸린다.

   ```
   kubectl annotate scaledobject gemma4-12b-vllm -n llm-serving \
     autoscaling.keda.sh/paused-replicas="2" --overwrite
   kubectl rollout status deployment/gemma4-12b-vllm -n llm-serving --timeout=15m
   ```

5. 고장 난 노드의 NodeClaim을 지운다. Karpenter가 파드를 내보내고 인스턴스를 종료한다.

   ```
   NODECLAIM=$(kubectl get nodeclaims -o json \
     | jq -r --arg n "${NODE}" '.items[] | select(.status.nodeName == $n) | .metadata.name')
   kubectl delete nodeclaim "${NODECLAIM}"
   ```

6. 자동 조절을 다시 켠다.

   ```
   kubectl annotate scaledobject gemma4-12b-vllm -n llm-serving autoscaling.keda.sh/paused-replicas-
   ```

이 절차를 자동화하려면 EKS 노드 모니터링 에이전트와 Karpenter의 노드 자동 복구를 함께 쓴다.

- **노드 모니터링 에이전트:** GPU 문제를 감지하면 노드에 `AcceleratedHardwareReady=False` 조건을 붙인다.
- **노드 자동 복구:** Karpenter의 `NodeRepair` 기능 게이트를 켜면, 이 조건이 10분 이어진 노드를 교체한다.
- **주의할 점:**
  - Karpenter 1.15 미만에서는 복구할 때 파드를 짧은 유예 시간으로 지우고 PodDisruptionBudget도 무시한다.
  - 노드 모니터링 에이전트는 자체 DCGM 호스트 엔진을 함께 띄운다. 그래서 DCGM Exporter와 같은 호스트 엔진을 쓰도록 맞출지 먼저 검토한다.

조건은 kube-state-metrics로도 볼 수 있다.

```
kube_node_status_condition{condition="AcceleratedHardwareReady", status="false"} == 1
```

### 7. 알림 규칙 ###

6절의 판단 기준을 PrometheusRule로 만든다. kube-prometheus-stack은 레이블과 상관없이 모든 PrometheusRule을 읽도록 설정돼 있다(KEDA 장 2절).

```
kubectl apply -f - <<'EOF'
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: gpu-alerts
  namespace: monitoring
spec:
  groups:
    - name: gpu-hardware
      rules:
        - alert: GPUXidHardwareError
          expr: |
            DCGM_FI_DEV_XID_ERROR == 48 or DCGM_FI_DEV_XID_ERROR == 64 or DCGM_FI_DEV_XID_ERROR == 79
            or DCGM_FI_DEV_XID_ERROR == 92 or DCGM_FI_DEV_XID_ERROR == 94 or DCGM_FI_DEV_XID_ERROR == 95
            or DCGM_FI_DEV_XID_ERROR == 119 or DCGM_FI_DEV_XID_ERROR == 120 or DCGM_FI_DEV_XID_ERROR == 154
          labels:
            severity: critical
          annotations:
            summary: "GPU 하드웨어 XID {{ $value }} (노드 {{ $labels.node }}, GPU {{ $labels.gpu }})"
            description: "하드웨어·펌웨어 계열 XID가 발생했다. 증거를 남기고 노드를 교체한다."

        - alert: GPUXidApplicationError
          expr: |
            (DCGM_FI_DEV_XID_ERROR == 13 or DCGM_FI_DEV_XID_ERROR == 31
             or DCGM_FI_DEV_XID_ERROR == 43 or DCGM_FI_DEV_XID_ERROR == 45)
            and changes(DCGM_FI_DEV_XID_ERROR[10m]) > 0
          labels:
            severity: warning
          annotations:
            summary: "애플리케이션 XID {{ $value }} (노드 {{ $labels.node }}, GPU {{ $labels.gpu }})"
            description: "vLLM 로그를 확인한다. 같은 노드에서 반복되면 하드웨어를 의심한다."

        - alert: GPUEccDoubleBitError
          expr: increase(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL[10m]) > 0
          labels:
            severity: critical
          annotations:
            summary: "정정 불가 ECC 오류 (노드 {{ $labels.node }}, GPU {{ $labels.gpu }})"

        - alert: GPURowRemapFailed
          expr: DCGM_FI_DEV_ROW_REMAP_FAILED == 1
          labels:
            severity: critical
          annotations:
            summary: "GPU 메모리 행 리매핑 실패 (노드 {{ $labels.node }}, GPU {{ $labels.gpu }})"

        - alert: GPUHighTemperature
          expr: max by (node, gpu) (DCGM_FI_DEV_GPU_TEMP_CELSIUS) > 85
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "GPU 온도 {{ $value }}°C (노드 {{ $labels.node }}, GPU {{ $labels.gpu }})"

        - alert: GPUThermalThrottling
          expr: rate(DCGM_FI_DEV_GPU_THERMAL_THROTTLE_SECONDS_TOTAL[5m]) > 0.1
          for: 10m
          labels:
            severity: warning
          annotations:
            summary: "GPU 온도 스로틀링 (노드 {{ $labels.node }}, GPU {{ $labels.gpu }})"

        - alert: GPUPcieReplayIncreasing
          expr: rate(DCGM_FI_DEV_PCIE_REPLAY_TOTAL[15m]) > 0
          for: 30m
          labels:
            severity: warning
          annotations:
            summary: "PCIe 재전송이 계속 늘어난다 (노드 {{ $labels.node }}, GPU {{ $labels.gpu }})"

    - name: gpu-capacity
      rules:
        - alert: GPUMetricsMissing
          expr: |
            kube_node_status_capacity{resource="nvidia_com_gpu"} > 0
            unless on (node) DCGM_FI_DEV_GPU_TEMP_CELSIUS
          for: 10m
          labels:
            severity: critical
          annotations:
            summary: "GPU 노드 {{ $labels.node }}에서 DCGM 지표가 없다"
            description: "GPU가 버스에서 떨어졌거나(XID 79) DCGM Exporter가 동작하지 않는다."

        - alert: GPUAllocatableLessThanCapacity
          expr: kube_node_status_allocatable{resource="nvidia_com_gpu"} < kube_node_status_capacity{resource="nvidia_com_gpu"}
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "노드 {{ $labels.node }}의 GPU가 할당 가능 목록에서 빠졌다"

        - alert: GPUNodeNotReady
          expr: |
            kube_node_status_condition{condition="Ready", status="true"} == 0
            and on (node) kube_node_status_capacity{resource="nvidia_com_gpu"} > 0
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "GPU 노드 {{ $labels.node }}가 NotReady"

    - name: inference
      rules:
        - alert: VLLMEngineStalled
          expr: |
            sum by (pod) (vllm:num_requests_running{namespace="llm-serving"}) > 0
            and sum by (pod) (rate(vllm:generation_tokens_total{namespace="llm-serving"}[5m])) == 0
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "vLLM 파드 {{ $labels.pod }}가 요청을 받은 채 토큰을 만들지 않는다"
EOF
```

- **XID 지표의 특성:** `DCGM_FI_DEV_XID_ERROR`는 마지막 코드를 계속 들고 있다.
  - 하드웨어 XID 알림은 노드를 교체할 때까지 계속 울린다. 의도한 동작이다.
  - 애플리케이션 XID 알림은 값이 새로 바뀐 경우(`changes`)에만 울린다.
- **XID 63은 넣지 않았다:** 메모리 행을 대체 기록했다는 알림이라 바로 장애로 보지 않는다. 대신 행 리매핑 지표로 본다.

규칙이 로드됐는지 확인한다. 상태는 평소 `inactive`이고, 조건을 만족하면 `pending`을 거쳐 `firing`이 된다.

```
kubectl get prometheusrule gpu-alerts -n monitoring

curl -s http://localhost:9090/api/v1/rules | jq -r '
  .data.groups[] | select(.name == "gpu-hardware" or .name == "gpu-capacity" or .name == "inference")
  | .rules[] | "\(.name)  \(.state)"'
```

Alertmanager에는 아직 수신처가 없다. 그래서 알림은 Prometheus UI의 Alerts 탭과 8절 대시보드의 "발생 중인 GPU 알림"에서 본다. Slack 연동은 EFA 모니터링 장의 Alertmanager 예시를 참고한다.

#### 8.2 NVIDIA 기본 대시보드 가져오기 ####

DCGM Exporter 저장소에는 4.9.0의 새 지표 이름에 맞춘 대시보드가 들어 있다. 예전 지표 이름을 쓰는 커뮤니티 대시보드는 데이터가 나오지 않으므로, 설치한 버전의 저장소에 있는 파일을 쓴다.

```
curl -sL -o dcgm-exporter-dashboard.json \
  https://raw.githubusercontent.com/NVIDIA/dcgm-exporter/${DCGM_EXPORTER_VERSION}/grafana/dcgm-exporter-dashboard.json
```

1. Grafana에서 **Dashboards > New > Import**를 연다.
2. 받은 JSON 파일을 업로드하고 데이터 소스로 Prometheus를 고른다.

GPU별 온도, 전력, 클럭, 사용률, 메모리, 텐서 코어 사용률 패널이 들어 있다.

#### 8.3 추론 클러스터용 대시보드 구성 ####

NVIDIA 대시보드는 GPU 하드웨어만 보여 준다. 워크샵에서는 GPU, 쿠버네티스, vLLM을 한 화면에서 보는 대시보드를 따로 만든다. 구성은 아래와 같다.

| 행 | 패널 | 종류 | 쿼리 요약 | 단위 |
|---|---|---|---|---|
| 요약 | GPU 노드 수 | Stat | DCGM 지표가 있는 노드 수 | 개 |
| 요약 | 할당 가능 / 전체 GPU | Stat | `kube_node_status_allocatable`, `_capacity` | 개 |
| 요약 | GPU 할당률 | Stat | GPU 요청 / 할당 가능 | % |
| 요약 | vLLM 레플리카 (Ready / 목표) | Stat | Deployment available, HPA desired | 개 |
| 요약 | 발생 중인 GPU 알림 | Stat | `ALERTS{alertstate="firing"}` | 개 |
| GPU 부하 | GPU 사용률 | Time series | `DCGM_FI_DEV_GPU_UTIL_RATIO` | % |
| GPU 부하 | 엔진 활성 비율 (DCP) | Time series | 텐서, DRAM, SM 활성 비율 | % |
| 메모리 | GPU 메모리 사용 비율 | Time series | FB 사용량 / 용량 | % |
| 메모리 | vLLM KV 캐시 사용률 | Time series | `vllm:kv_cache_usage_perc` | % |
| 열·전력·클럭 | 온도 | Time series | GPU·메모리 온도 | °C |
| 열·전력·클럭 | 전력 | Time series | 소비 전력, 전력 한도 | W |
| 열·전력·클럭 | SM 클럭 | Time series | `DCGM_FI_DEV_SM_CLOCK_HERTZ` | Hz |
| 열·전력·클럭 | 스로틀링 시간 비율 | Time series | 온도·전력 스로틀링 `rate` | % |
| 열·전력·클럭 | PCIe 처리량 | Time series | PCIe RX, TX | bytes/s |
| 추론 서비스 | 생성 토큰 처리량 | Time series | `rate(vllm:generation_tokens_total)` | tokens/s |
| 추론 서비스 | 동시 요청 | Time series | running, waiting | 개 |
| 추론 서비스 | 토큰당 GPU 에너지 | Time series | 에너지 rate / 토큰 rate | J |
| 장애 신호 | 마지막 XID 코드 | Table | `DCGM_FI_DEV_XID_ERROR` (즉시 조회) | 코드 |
| 장애 신호 | 할당 가능 GPU / 용량 | Time series | 노드별 allocatable, capacity | 개 |
| 장애 신호 | ECC·행 리매핑·PCIe 재전송 | Time series | 1시간 증가량, 리매핑 실패 | 개 |

- **아래쪽 행:** "왜 그런가"를 답한다.
- **노드 변수:** 대시보드 위쪽의 `node` 변수로 GPU 노드를 골라 볼 수 있다.

#### 8.4 대시보드 읽는 법 ####

- **모델 기동 중:** PCIe "호스트→GPU"가 크게 오르고 GPU 메모리 사용 비율이 0.9까지 올라간 뒤 평평해진다. 그 뒤 토큰 처리량이 나오기 시작한다.
- **부하가 늘 때:** 동시 요청, KV 캐시 사용률, DRAM 활성 비율이 함께 오른다. GPU 사용률은 이미 1 근처라 변화가 거의 없다.
- **스로틀링:** 온도나 전력이 한도에 붙은 구간에 SM 클럭이 떨어지고, 스로틀링 시간 비율과 토큰당 에너지가 오른다.
- **장애:**
  - "발생 중인 GPU 알림"이 빨간색으로 바뀐다.
  - "마지막 XID 코드" 표에 0이 아닌 값이 보인다.
  - "할당 가능 GPU"가 용량보다 낮아진다.
  - 이때는 6.2절 절차로 대응한다.

### 9. 문제 해결 ###

| 증상 | 확인할 것 |
|---|---|
| DCGM Exporter 파드가 Pending이다 | GPU 노드의 테인트(`nvidia.com/gpu`)를 허용하는지, `nodeSelector`의 노드풀 이름이 맞는지 본다. |
| 파드가 CrashLoopBackOff다 | `kubectl logs -n monitoring daemonset/dcgm-exporter`로 본다. 지표 이름 오류면 2.2절 목록의 이름을 확인한다. GPU를 찾지 못한다는 오류면 노드의 기본 컨테이너 런타임이 NVIDIA 런타임인지 확인하고, 아니면 차트의 `runtimeClassName`을 지정한다. |
| `DCGM_FI_PROF_*` 지표만 없다 | 프로파일링 지표는 `SYS_ADMIN` 권한이 필요하다. 차트 기본 `securityContext`를 바꾸지 않았는지 본다. 같은 노드에서 다른 DCGM 호스트 엔진이 프로파일링 카운터를 쓰고 있는지도 확인한다. |
| `exported_pod` 레이블이 비어 있다 | 그 GPU를 쓰는 파드가 없거나, kubelet pod-resources 경로(`/var/lib/kubelet/pod-resources`)가 마운트되지 않았다. |
| 대시보드의 `node` 변수가 비어 있다 | ServiceMonitor relabeling이 적용됐는지 본다. `DCGM_FI_DEV_GPU_TEMP_CELSIUS`에 `node` 레이블이 있어야 한다. |
| 커뮤니티 대시보드에 데이터가 없다 | 4.9.0 이전 지표 이름을 쓰는 대시보드다. 8.2절의 대시보드나 8.3절의 대시보드를 쓴다. |

### 10. 정리 ###

```
kubectl delete configmap grafana-dashboard-gpu-inference -n monitoring
kubectl delete prometheusrule gpu-alerts -n monitoring
helm uninstall dcgm-exporter -n monitoring

kill ${PROM_PID} 2>/dev/null
```
